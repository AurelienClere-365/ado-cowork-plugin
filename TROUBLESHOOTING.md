# Troubleshooting & Monitoring

This guide is for after the plugin has been deployed and is in day-to-day use. If a
user reports "it's not working" and you don't know why, start here.

It covers all three deployment options, but most of the depth is on **Option C (M365
Copilot)** since that is the recommended, org-wide deployment and the hardest one to
observe — there is no local console or log file to tail.

---

## Quick triage checklist

Before digging into logs, rule out the common causes in order:

1. **Is the plugin enabled?** Microsoft 365 Copilot → **Sources & Skills** (or
   **Get agents**) → confirm **ADO Cowork** appears and is toggled on for the affected
   user.
2. **Has the user consented?** OAuthPluginVault (Option C) requires each user to
   consent once via the OAuth flow on first use. If they never saw or dismissed the
   consent prompt, every call will fail silently from their point of view.
3. **Did the client secret expire?** See [Secret expiry](#secret-expiry) below — this is
   the single most common cause of a tenant-wide outage that "used to work."
4. **Is `mcpServerUrl` correct?** Check `manifest.json` still has the real org name
   (not `contoso`) and matches `https://mcp.dev.azure.com/{orgName}`.
5. **Does the user actually have Azure DevOps access?** OAuthPluginVault only proves
   identity — Azure DevOps still enforces its own project/org permissions. A user with
   no access to the ADO org or project will get empty or denied results, not a
   plugin error.
6. **Reproduce with a minimal prompt.** Ask the affected user (or reproduce yourself)
   with: `"Show me all organisations I have access to in Azure DevOps."` This exercises
   `ado-context` → `core_list_projects` with no other skill logic involved, isolating
   connectivity/auth problems from skill-routing problems.

## "Authentication is still processing. Please try again."

This message is generated by Microsoft 365 Copilot's OAuth consent flow (the
`OAuthPluginVault` handshake with Azure DevOps' `mcp.dev.azure.com`), not by any code in
this repository — there is nothing to "fix" in the plugin itself, but it can be
diagnosed:

1. **Understand what the message means.** It typically appears when the OAuth
   consent/token exchange hasn't completed yet — either the user dismissed or never
   finished the consent prompt, or Copilot is waiting on a token that never arrived.
2. **Confirm the deployment option in use** (per [README.md — Deployment
   options](README.md#deployment-options) and `manifest.json`). If this is **Option C**
   (M365 Copilot with `OAuthPluginVault`), the checklist below applies. If it's
   **Option B** (local MCP/VS Code), the cause is different — see [Sign-in
   issues](#option-b--local-mcp-vs-code).
3. **Follow the [Quick triage checklist](#quick-triage-checklist) above**, in
   particular:
   - Confirm the plugin is enabled for the user (**Sources & Skills** / **Get agents**).
   - Confirm the user actually completed the one-time OAuth consent prompt — don't just
     dismiss it, go through it fully.
   - Check whether the Azure AD app registration's client secret has expired
     (**Entra ID** → **App registrations** → **Certificates & secrets** → **Expires**
     column) — see [Secret expiry](#secret-expiry) below; this is the most common cause
     of "auth-shaped" failures that look stuck/silent.
   - Verify `manifest.json`'s `mcpServerUrl` matches the real org name and
     `authorization.type` is `OAuthPluginVault`.
4. **Check [Entra ID sign-in logs](#entra-id-sign-in-logs-the-closest-thing-to-a-request-log)**
   (**Identity** → **Monitoring & health** → **Sign-in logs**, filtered to the app
   registration) for `Failure` entries with an AADSTS error code around the time of the
   failure — this shows whether the consent/token request is failing, being blocked by
   Conditional Access, or genuinely stuck.
5. **Reproduce with a minimal prompt** (e.g., `"Show me all organisations I have access
   to in Azure DevOps."`) to isolate whether this is a general auth failure vs. a
   skill-specific issue.
6. **If unresolved**, use the [Escalation checklist](#escalation-checklist) below to
   gather: deployment option, exact prompt/error text, timestamp, affected users,
   sign-in log entry, secret expiry status, and `manifest.json` settings — then
   escalate to Microsoft 365 support, Azure DevOps support, or the plugin maintainer.

## Option C — M365 Copilot (recommended, org-wide)

This is the deployment most teams run, and the one where "we don't know why it failed"
is most likely to come up, because there is no local terminal or log file — everything
happens inside Microsoft 365 and Entra ID (Azure AD).

### Where to look

| Symptom | Where to check | What to look for |
|---|---|---|
| Plugin missing from Sources & Skills | M365 Admin Centre → **Agents** → **All agents** | Plugin present, status = published, not disabled/blocked by a Copilot policy |
| "I don't have a way to connect to Azure DevOps from here" | `manifest.json` → `authorization.type` | Must be `OAuthPluginVault`, not `None` — see [README Step 6](README.md#step-6--authentication-required-for-mcp-tools-to-work) |
| Auth works for some users, not others | Entra ID → **Enterprise applications** → your app registration → **Users and groups** / **Sign-in logs** | Confirm the user's account isn't blocked by Conditional Access, MFA, or app assignment scope |
| Everyone suddenly fails at once | Entra ID → **App registrations** → your app → **Certificates & secrets** | Check the client secret **Expires** column — see [Secret expiry](#secret-expiry) |
| Auth succeeds, ADO calls fail or return empty | Azure DevOps → **Organization settings** → **Users** | Confirm the signed-in user is a member of the org/project with at least Basic access |
| Intermittent failures / timeouts | Entra ID **Sign-in logs**, filtered to the app registration | Look for `interrupted` or throttling (HTTP 429) entries around the failure time |
| Plugin responds but with the wrong data / stale skill behaviour | `manifest.json` `version` vs. what's actually installed | Confirm the tenant was updated (**Agents → All agents → ADO Cowork → Update**) after the last skill change, per [Updating the plugin](README.md#updating-the-plugin-eg-upgrading-an-existing-110-tenant-to-120) |

### Entra ID sign-in logs (the closest thing to a "request log")

Because `mcp.dev.azure.com` sits behind Azure AD, every OAuth token exchange for the app
registration created in [README Step 6a](README.md#6a--create-an-azure-ad-app-registration)
shows up in Entra ID:

1. [entra.microsoft.com](https://entra.microsoft.com) → **Identity** → **Monitoring &
   health** → **Sign-in logs**.
2. Filter **Application** to the app registration name (e.g. `ADO Cowork Plugin`).
3. Look at the **Status** column — `Failure` entries include an error code
   (e.g. `AADSTS65001` = user or admin hasn't consented, `AADSTS700016` = app not found
   in tenant, `AADSTS7000215` = invalid client secret).
4. Click a failed sign-in to see the **Conditional Access** tab — this shows if a
   Conditional Access policy blocked the request before it ever reached Azure DevOps.

This is the primary signal for "auth-shaped" failures (the plugin can't connect at all,
regardless of what the user asked).

### Secret expiry

The Azure AD app registration's client secret (created in Step 6a, or via
`setup-auth.ps1`) has an expiry date. When it lapses, `mcp.dev.azure.com` rejects every
user's token refresh **silently** — the plugin will appear broken tenant-wide with no
obvious error message pointing at the cause.

- Check the expiry: **Entra ID** → **App registrations** → your app →
  **Certificates & secrets** → **Expires** column.
- `setup-auth.ps1` prints the expiry date when it creates a secret and defaults to 12
  months (`-SecretExpiryMonths`). Set a calendar reminder ahead of that date.
- To recover: rotate the secret in the Azure Portal (or re-run `setup-auth.ps1`), then
  patch `manifest.json`/re-upload if the `referenceId` changed. See
  [SECURITY.md#secret-rotation](SECURITY.md#secret-rotation) for the full procedure.

### Azure DevOps-side signal

Azure DevOps does not expose per-request logs to plugin authors, but you can confirm
whether calls are reaching it at all:

- **Organization settings → Auditing** (if enabled on the org) records API/OAuth-token
  activity, including the app registration's client ID, which helps confirm calls are
  arriving from the expected app.
- If audit logging isn't enabled, the absence of any related audit or usage change is
  itself a signal that requests aren't reaching Azure DevOps — which points back to the
  M365/Entra ID side (auth, Conditional Access, or the plugin not being enabled).

### Microsoft 365 admin & Copilot usage reports

**M365 Admin Centre** → **Reports** → **Usage** → **Microsoft 365 Copilot** shows
adoption and activity at a tenant level (which users are actively using Copilot).
This doesn't give per-skill or per-tool detail, but it's useful to confirm a user is
actually reaching Copilot at all before assuming the plugin itself is at fault.

## Option B — Local MCP (VS Code)

This is the easiest option to debug because everything runs on the developer's own
machine with visible logs.

- **VS Code Output panel** → select **GitHub Copilot Chat** (or **MCP**, depending on
  VS Code version) from the dropdown — this shows the MCP server connection status,
  handshake errors, and tool call/response payloads.
- **Command Palette** → `MCP: List Servers` (or `Azure DevOps` in the extension's own
  panel, if using the Azure DevOps extension for Azure AD sign-in) — confirms the
  server is registered and its current connection state.
- **Sign-in issues**: run `Azure: Sign In` from the Command Palette. If VS Code's Azure
  AD session has expired or is using the wrong tenant/account, `mcp.dev.azure.com` will
  reject every call the same way it does in Option C.
- **Config errors**: verify `mcp.json` (`%APPDATA%\Code\User\mcp.json` or
  `.vscode/mcp.json`) has the correct org name in the URL — a typo here produces a
  connection failure that looks identical to an auth failure.

## Option A — Skills-only

There is no MCP server and no network call in this mode — skills only shape how
Copilot Chat/Agent phrases and routes requests, using whatever ADO access the user's
existing tools already have. If something looks wrong here, the issue is almost always:

- The skill files weren't copied to the expected prompts folder — re-run
  `.\package.ps1 -SkillsOnly` and check the copy step completed.
- The behaviour the user expected actually requires a live MCP connection (Option B or
  C) — Skills-only cannot call any ADO API on its own.

## Escalation checklist

If you've worked through the above and still can't explain a failure, capture the
following before escalating (to Microsoft 365 support, Azure DevOps support, or the
plugin maintainer):

- [ ] Deployment option in use (A / B / C) and `manifest.json` `version`
- [ ] Exact user prompt and the exact response/error text received
- [ ] Timestamp (with timezone) of the failure
- [ ] Affected user(s) — one user, a subset, or everyone in the tenant
- [ ] Entra ID sign-in log entry for that timestamp/app registration, if Option C
- [ ] Whether the client secret is still valid (expiry date)
- [ ] `manifest.json` `mcpServerUrl` and `authorization.type` (never share the actual
      secret value or `referenceId` outside your organisation)
